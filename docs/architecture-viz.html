🏛️ 总览：三层架构

Collabora Online 将 LibreOffice 搬到 Web/移动端。核心思路：浏览器只管显示，服务端负责渲染。

WSD = Web Services Daemon
Kit = LibreOfficeKit 进程
ForKit = Kit Forker
WOPI = Web Application Open Platform Interface
🧠 核心分工记忆：
• WSD = 大脑（调度、存储、缓存、权限、路由）
• Kit = 手（实际操控 LibreOffice，渲染文档、处理输入）
• ForKit = 产房（预初始化 LOKit，按需 fork 出新 Kit）
• 三者通过 WebSocket 通信，各自运行在独立进程中（沙箱隔离）
📱 Mobile (Android/iOS) 特殊之处：
Mobile 端 WSD 和 Kit 运行在 同一进程 中（通过 FakeSocket 模拟 WebSocket）， 只有 一个 DocumentBroker 和一个 Kit。 没有 ForKit 进程，没有 chroot jail 沙箱。

2. 通信路径总图

🔑 关键：Socket 转移 (SocketDisposition)

浏览器连接 WSD 时，Socket 先归属于 WSD 主 Poll。 WSD 解析 URL 确定目标文档后，通过 SocketDisposition::setTransfer() 将 Socket 转移到对应 DocumentBroker 的 Poll 线程。

这样设计的目的是 每个文档的 I/O 完全独立，不会因为一个文档繁忙而阻塞其他文档。

🧩 Tile 体系

什么是 Tile？为什么用 Tile？

文档（如 Writer 文档）可能非常大（如 20000×30000 像素），如果一次性渲染整个文档再传给浏览器， 内存和带宽都不可接受。因此将文档画布切分成 256×256 像素的小方块（Tile）， 只渲染用户当前可见区域内的 Tile。

核心类

类文件职责
TileDesc wsd/TileDesc.hpp Tile 描述符：坐标、尺寸、part、viewId、zoom、版本号
TileCombined wsd/TileDesc.hpp 多个 Tile 的组合请求，一次渲染多个
TilePrioritizer kit/KitQueue.hpp Tile 渲染优先级：光标位置 > 可视中心 > 边缘
TileCache wsd/TileCache.cpp WSD 端缓存已渲染 Tile，避免重复请求
DeltaGenerator kit/Delta.hpp 比较新旧 Tile 像素，生成增量 keyframe/delta + SIMD 加速
💡 Delta 优化： 用户编辑文档后，大部分 Tile 内容不变。Delta 只传输 变化的像素区域， 而非整个 256×256 Tile，大幅减少网络流量。浏览器端 ClientDeltaTracker 负责拼合 Delta。

🧠 llama.cpp 原理解析

llama.cpp 是一个纯 C/C++ 实现的 LLM 推理引擎。它的核心使命：在消费级设备上（无 GPU）高效运行大型语言模型。

一句话总结

llama.cpp 把一个训练好的模型文件（GGUF 格式）加载到内存，用 量化压缩 减少内存占用， 再通过 手写 SIMD 优化的矩阵运算（ggml 张量库）在 CPU 上逐 token 生成文本。

1. 从用户输入到 AI 输出 — 完整推理流水线

2. 两大阶段：Prefill vs Decode

💡 为什么 Prefill 用 BATCH_SIZE=128 分批？
长 prompt (如 5000 tokens) 若一次全喂入，内存峰值巨大。 分 128 token/批 处理，每批之间可释放中间张量，内存更可控。 同时每 5 秒输出心跳日志防止用户以为卡死了。

3. GGUF 格式与量化

量化格式每权重 bit 数1.5B 模型大小质量适用场景
FP1616~3.0 GB原始精度服务端部署
Q8_08~1.6 GB几乎无损高性能桌面
Q4_K_M~4.5~1.1 GB✓ 本项目的选择移动端 / 边缘设备
Q2_K~2.5~0.6 GB有损极低内存设备

GGUF（GGML Universal Format）是 llama.cpp 自有的模型文件格式，统一包含： 模型权重（量化后的 tensor）+ tokenizer 词表 + 超参数（n_layers, n_heads, n_embd 等）+ chat template + 元数据。 一个 .gguf 文件 = 完整的可部署模型。

5. ggml 后端 — 手写 SIMD 加速

llama.cpp 的核心计算库 ggml 是一个纯 C 的张量计算库，不含任何外部依赖（不需要 BLAS/CUDA/cuDNN）。 它在不同 CPU 架构上使用手写 SIMD 指令（ARM NEON / x86 AVX2 / AVX512）加速矩阵乘法。

本项目的 Android arm64-v8a 构建启用了 KleidiAI（ARM 官方优化的矩阵乘法内核）， 同时禁用了 OpenMP（避免与 LibreOfficeKit 的线程池竞争 libomp 状态导致死锁）。

6. 关键设计决策

决策选择原因
模型格式 GGUF Q4_K_M (4.5-bit) 质量与大小的最佳平衡点，1.5B 模型只需 1.1GB
推理线程 单线程 Executor 避免 JNI 并发冲突，简化全局状态管理 (g_model, g_ctx 全局变量)
模型加载 懒加载 (首次 execute 时) 不启动 App 就占用 1.6GB 内存
KV Cache 清理 每次请求前 clear 保证多轮对话之间状态隔离（multiTurn=false 时）
异常恢复 smoke_decode_test 模型加载后立即用 "hi" 做一次试推理，失败则回滚所有资源
心跳日志 每 5 秒输出进度 长推理时防止误判 ANR，辅助排障
💡 为什么 Context Size 只有 4096？
Qwen2.5-1.5B 原生支持 32K 上下文，但移动端内存有限： KV Cache 大小 ≈ n_layers × n_ctx × n_embd × 2 × 2 bytes (FP16)。4096 tokens 约需 500MB KV Cache， 加上模型 1.1GB，总计内存控制在 ~1.6GB，确保 4GB RAM 设备上稳定运行。 8GB+ 设备可扩展到 contextSize=4096, maxTokens=512。
